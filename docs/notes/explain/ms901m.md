# MS901M 姿态传感器驱动模块 学习笔记

## 📖 一、整体概述

### 1.1 项目背景

本项目是一个**两轮自平衡瞄准小车**（详见 `docs/Overview/Overview.md`），
主控芯片为 **TI MSPM0G3507**（Cortex-M0+ 内核，80 MHz，无 FPU 浮点运算单元）。

为了让小车能够保持平衡，我们需要实时获知车身的**倾斜角度**（俯仰角 pitch）和**倾斜角速度**（pitch_rate）。
MS901M 就是一个负责提供这些数据的**姿态传感器**（也叫 IMU：Inertial Measurement Unit，惯性测量单元）。

### 1.3 MS901M 传感器简介

MS901M 是一款**串口输出**的姿态传感器，特点：

- 内部集成了**陀螺仪**（测角速度）、**加速度计**（测加速度）、**磁力计**（测磁场）、**气压计**（测气压/高度）
- 自带一颗 MCU 做**姿态解算**（运行十五阶卡尔曼滤波器），直接输出经过融合的姿态角
- **上电即主动输出**：不需要单片机主动问它要数据，它会一直自己往外发数据帧
- 默认 **200 Hz** 输出频率（每 5 毫秒一帧）
- 输出协议：**二进制帧**（不是文本，不能直接"读"）

### 4.2 核心状态机运行逻辑

状态机是解析器的"大脑"，它用 6 个状态来跟踪当前正在处理的字节位于帧的哪个位置：

```
接收到的字节        状态变化                     做了什么
────────────────  ──────────                  ──────────
字节 = 0x55       ST_SYNC1 → ST_SYNC2         记下 sum = 0x55
字节 = 0x55       ST_SYNC2 → ST_ID            sum += 0x55
字节 = 0x01       ST_ID → ST_LEN              s_id = 0x01, sum += 0x01
字节 = 0x06       ST_LEN → ST_DATA            s_len = 6, sum += 0x06, 准备收6字节
字节 = 0x12       ST_DATA(收第1个)             s_data[0]=0x12, sum += 0x12
字节 = 0x34       ST_DATA(收第2个)             s_data[1]=0x34, sum += 0x34
...继续收4个...     ST_DATA                     ...
收完6个后           ST_DATA → ST_CHECKSUM      等待校验和
字节 = sum值       ST_CHECKSUM → ST_SYNC1     校验通过！解析数据帧, good++
字节 = 其他值      ST_CHECKSUM → ST_SYNC1     校验失败, bad++后丢弃
```

**关键点**：
- 状态机**逐字节推进**，不需要先把整帧收完再处理，节省了缓冲空间
- 任何不匹配的字节都会导致状态机**回到 ST_SYNC1 重新同步**，这保证了即使偶尔有错位也能快速恢复
- 校验和是**边收边算**的，不是收完再算一遍，效率更高

### 4.3 数据帧解析与换算公式

MS901M 发送的原始数据是 **int16**（16 位有符号整数），范围 -32768 ~ +32767。
我们需要把它换算成真实的物理量。

#### 姿态角（0x01 帧）

```
pitch_deg = int16原始值 × (180° / 32768)
```

举例：如果原始值 = 16384（十六进制 0x4000）
则 pitch = 16384 × (180 / 32768) = 16384 × 0.005493 = **90°**

#### 陀螺仪（0x03 帧，默认 ±2000 dps）

```
gy_dps = int16原始值 × (2000 dps / 32768)
       = int16原始值 × 0.0610
```

举例：如果原始值 = 3277，则 gy = 3277 × 0.0610 ≈ **200 °/s**

⚠️ **量程很重要**：如果传感器改为 ±500 dps 量程，但代码还用 2000 算，
同样的原始值 3277 会错误地算成 200 °/s，实际上应该是 50 °/s。

#### 加速度计（0x03 帧，默认 ±4g）

```
ax_g = int16原始值 × (4g / 32768)
```

举例：如果原始值 = 16384，则 ax = 16384 × 0.000122 = **2.0g**
静态放置时，三个轴的平方和 ≈ 1.0g²（重力加速度）。

#### 温度（0x04 帧）

```
temp_c = int16原始值 / 100
```

举例：原始值 = 2545 → temp = 2545 / 100 = **25.45°C**

### 4.4 命令帧构造逻辑

本项目不仅接收传感器数据，也可以向传感器发送命令。

#### 区分读写命令

| 命令类型 | 帧头 | ID 范围 | 说明 |
|---------|------|---------|------|
| **读命令** | 0x55 0xAF | 0x80~0xFF（原 ID OR 0x80） | 读取寄存器当前值 |
| **写命令** | 0x55 0xAF | 0x00~0x7F（原 ID 不变） | 写入新配置 |

为什么读命令的 ID 要 OR 0x80？这是 MS901M 的协议约定：
- 最高位为 1 → 表示这是一次读取操作
- 最高位为 0 → 表示这是一次写入操作

#### 写命令帧结构示例

```
设置加速度计量程为 ±8g：
  0x55  0xAF  0x04  0x01  0x02  校验和
  ↑     ↑     ↑     ↑     ↑     ↑
  sync1 sync2 ID    LEN   DATA  SUM
  (0x04=ACCFSR命令)  (1字节)  (0x02=±8g)
```

#### 校验和计算方法

```c
sum = 0x55 + 0xAF + 0x04 + 0x01 + 0x02 = 0x0105
校验和 = sum & 0xFF = 0x05    // 只取低 8 位
```

### 4.5 模块的使用方式（典型调用序列）

```c
// ==== 第一步：初始化（上电时调用一次） ====
ms901m_init(4, 2000);   // 加速度 ±4g，陀螺 ±2000 dps

// ==== 第二步：等待 IMU 上线 ====
while (!ms901m_has_attitude()) {
    uint8_t buf[64];
    size_t n = uart_read(buf, sizeof(buf));  // 从串口取数据
    if (n > 0) ms901m_feed_bytes(buf, n);    // 喂给解析器
}

// ==== 第三步：主循环中持续获取数据 ====
for (;;) {
    // 每 1 ms 刷新数据
    uint8_t buf[64];
    size_t n = uart_read(buf, sizeof(buf));
    if (n > 0) ms901m_feed_bytes(buf, n);

    // 每 5 ms 取一次快照用于控制
    if (time_elapsed >= 5) {
        ms901m_snapshot_t snap;
        ms901m_get_snapshot(&snap);
        float pitch = snap.pitch_deg;   // 当前俯仰角
        float rate  = snap.gy_dps;      // 俯仰角速度
        // 把 pitch 和 rate 喂给 PD 控制器…
    }
}
```

### 4.6 易错点和常见陷阱

#### 陷阱 1：量程不匹配
- **现象**：角度/角速度数据看起来不对，偏大或偏小一个固定倍数
- **原因**：`ms901m_init()` 传入的量程和传感器实际配置不一致
- **解决**：用 ATK 上位机软件查看当前传感器配置，确保参数一致

#### 陷阱 2：波特率不匹配
- **现象**：`bad_frames` 持续快速增长
- **原因**：单片机 UART 波特率和 MS901M 的设置不一致
- **解决**：检查两块板子的波特率设置是否一致

#### 陷阱 3：校验和错误被忽略
- **初学者常见**：只关注 `pitch_deg` 的值，不看 `bad_frames` 计数
- **正确做法**：定期检查 `ms901m_bad_frames()`，如果增长过快说明通信链路有问题

#### 陷阱 4：大端 vs 小端
- MS901M 用的是**小端模式（Little-Endian）**：低地址存低字节
- MSPM0G3507 也是小端，所以不需要做字节序转换
- 但如果移植到其他平台（如 STM32 默认小端，但也匹配），要注意这个前提

#### 陷阱 5：float 精度
- 本项目特意用 `float` 而非 `double`，因为 Cortex-M0+ 无硬件 FPU
- `float` 是 32 位，`double` 是 64 位，软件模拟时 float 快 2~3 倍
- 平衡控制需要的精度（0.1°）用 float 完全足够

## 🧠 五、关键知识点讲解

### 5.1 什么是"状态机"？

**有限状态机（FSM）** 是一种编程模式，它把程序的行为分成有限个"状态"，
任何时候程序处于其中一个状态，接收到输入后根据当前状态决定下一步做什么。

**现实类比**：自动售货机
- 状态：等待投币 → 已投币 → 已选择商品 → 出货中
- 输入：投币按键 → 选择商品按键 → 确认按键
- 每个状态下，相同的输入可能产生不同的行为

**本模块的 6 个状态**：
```
ST_SYNC1 → ST_SYNC2 → ST_ID → ST_LEN → ST_DATA → ST_CHECKSUM → (回 ST_SYNC1)
```
每个状态只关心一件事：当前字节应该是什么、下一个字节应该是什么。

**为什么用状态机？**
- 适合**流式数据**处理（数据源源不断地来，不能等收完整帧再处理）
- 代码结构清晰，每个状态的处理逻辑独立
- 容易处理异常（非法字节 → 直接回到初始状态）

### 5.2 什么是"校验和"？

校验和是一种**错误检测**方法。发送方在数据末尾附加一个额外的字节，
这个字节的值 = 前面所有字节的**累加和取低 8 位**。
接收方用同样的方法计算一遍，如果结果和附加的字节不一致 → 数据在传输中损坏了。

**为什么需要校验和？**
串口通信在物理线路上传输时，可能受到电磁干扰（电机 PWM 就是很大的干扰源），
导致某些位被"翻转"（0 变 1 或 1 变 0）。校验和能检测出这类错误。

### 5.3 什么是"小端字节序"？

一个 16 位整数（如 0x1234）在内存中存放时有两种方式：
- **小端（Little-Endian）**：低地址放低字节 → `[0x34, 0x12]`
- **大端（Big-Endian）**：低地址放高字节 → `[0x12, 0x34]`

MS901M 和 MSPM0G3507 都是小端，所以 `le16()` 函数的实现就是简单的：
```c
(int16_t)((hi << 8) | lo)  // 低字节 + 高字节<<8
```

如果传感器是大端的，同样的数据会解读出完全不同的值。

### 5.4 什么是"头文件保护宏"？

```c
#ifndef MS901M_H    // 如果没有定义 MS901M_H 这个宏
#define MS901M_H    // 就定义它
// ... 头文件内容 ...
#endif              // 结束条件编译
```

这个结构称为 **include guard（包含保护）**。
如果一个项目里多个文件都 `#include "ms901m.h"`，
链接器不会重复编译头文件的内容，避免"重复定义"错误。

### 5.5 为什么用 static 修饰内部变量和函数？

`.c` 文件中，用 `static` 修饰的变量和函数：
- **只在当前文件内部可见**
- 其他 `.c` 文件无法访问（链接器会报错）
- 实现了"信息隐藏"——模块的内部细节对外部不可见

这符合软件工程的**封装原则**：
- 外部只能通过头文件声明的 11 个公开函数与本模块交互
- 内部的 6 个状态、3 个缓冲区、2 个换算系数对外部完全不可见
- 未来修改内部实现时，只要保持公开函数接口不变，外部代码无需改动

### 5.6 extern "C" 的作用

```c
#ifdef __cplusplus
extern "C" {
#endif
// ... 函数声明 ...
#ifdef __cplusplus
}
#endif
```

当 C 代码被 C++ 编译器编译时，C++ 会对函数名做"名字修饰"（name mangling），
导致链接器找不到 C 语言的函数符号。`extern "C"` 告诉 C++ 编译器：
"这里的函数用 C 的规则命名，不要修饰名字"。

因为 MSPM0G3507 项目是纯 C 环境，所以 `__cplusplus` 不会被定义，
这个保护块不会生效。它只是"以防万一"，如果将来某个模块用 C++ 编译器编译。

## 📝 七、快速问答

**Q：MS901M 每秒发多少帧数据？**
A：默认 200 Hz，即每秒 200 帧，每 5 毫秒一帧。

**Q：一帧数据有多少字节？**
A：取决于帧类型。姿态帧（0x01）= 2+1+1+6+1 = 11 字节；陀螺帧（0x03）= 17 字节。

**Q：单片机怎么知道收到的字节属于哪一帧？**
A：通过两个连续的 0x55 找到帧头。这也是为什么需要状态机——它不断在字节流中"找头"。

**Q：如果串口线受到干扰丢了一个字节会怎样？**
A：状态机会在下一个字节发现校验和不匹配，然后自动回到 SYNC1 状态重新同步。
下次正确的帧头出现时，状态机就能恢复。这通常只需要几十微秒。

**Q：为什么主循环里每 1 ms 就要喂字节？**
A：MS901M 的 200 Hz 输出意味着每 5 ms 就来一帧（约 11~17 字节）。
如果喂得太慢，环形缓冲区可能会满，导致数据丢失。
1 ms 喂一次是保守设计，确保缓冲区不会溢出。

**Q：为什么不用中断里直接解析？**
A：中断服务程序（ISR）应该尽可能短小精悍。
解析过程涉及浮点运算，在中断里做会严重影响系统的实时性。
中断只负责把收到的字节存入环形缓冲区，解析工作交给主循环轮询处理。

## 🧩 八、ms901m.c 代码逐段详解

### 8.1 文件头注释与 #include

```c
#include "ms901m.h"
```
`#include` 就是把 `ms901m.h` 的内容"粘贴"到这里。头文件里定义了本模块需要的一切：
- `ms901m_snapshot_t` 结构体（数据的"容器"）
- 所有枚举类型（命令 ID、量程选项等）
- 所有公开函数的声明

用引号 `""` 而不是尖括号 `<>`，表示这是"项目内部的头文件"，不是编译器标准库。

### 8.2 宏定义常量

```c
#define MS901M_DATA_MAX  32u
#define SYNC_BYTE        0x55u
```
- `#define` 是**编译预处理指令**：在编译前，预处理器把代码中所有的 `MS901M_DATA_MAX` 替换成 `32u`
- 用宏而不是变量的好处：
  1. **零内存开销**：宏不占用 RAM，编译后直接变成数字
  2. **只读性**：宏是常量，代码中无法意外修改
  3. **自文档化**：`MS901M_DATA_MAX` 比裸写的 `32` 更容易理解

**初学者易错点**：宏不是 C 语句，末尾不需要分号 `;`。
如果写了分号，宏展开后会变成 `32u;`，可能在某些上下文中引起语法错误。

`0x55` 的二进制是 `0b01010101`——0101 交替的模式便于接收方做时钟同步。

### 8.3 状态枚举

```c
typedef enum {
    ST_SYNC1 = 0,  // 等第一个 0x55
    ST_SYNC2,      // 等第二个 0x55
    ST_ID,         // 收帧类型 ID
    ST_LEN,        // 收数据长度
    ST_DATA,       // 收数据内容
    ST_CHECKSUM    // 收校验和
} parse_state_t;
```
枚举（enum）把数字映射成有意义的名称。编译器会把 `ST_SYNC1` 替换为 `0`、`ST_SYNC2` 替换为 `1`，以此类推。运行时零开销。

这 6 个状态对应了"从开始接收一帧到处理完一帧"的完整流水线。任何时候，解析器都处于其中一个状态。每个字节到来时，解析器根据当前状态决定怎么处理。

### 8.4 静态全局变量

```c
static parse_state_t s_state    = ST_SYNC1;
static uint8_t       s_id       = 0u;
static uint8_t       s_len      = 0u;
static uint8_t       s_data[MS901M_DATA_MAX];
static uint8_t       s_data_idx = 0u;
static uint8_t       s_chk      = 0u;
static float s_acc_scale  = 4.0f / 32768.0f;
static float s_gyro_scale = 2000.0f / 32768.0f;
static ms901m_snapshot_t s_snap = { 0 };
static uint32_t          s_bad_frames  = 0u;
static uint32_t          s_good_frames = 0u;
```

**static 关键字的作用**：
- 这些变量只在 `ms901m.c` 文件中可见，其他 `.c` 文件无法访问
- 实现了"封装"——模块内部状态对外部隐藏
- 函数返回后变量的值**保留不变**（不像局部变量会销毁）

**为什么需要这些"记住状态"的变量？**
因为 `ms901m_feed_bytes()` 每次只处理一批字节（比如 20 个），处理完返回。
下一次调用时，必须知道"上次处理到哪了"——是靠 `s_state` 这些静态变量来记住的。

**s_chk 的 uint8_t 溢出特性**：
`s_chk` 是 `uint8_t`（0~255），每次累加超出 255 时会自动"回绕"：
```
200 + 100 = 300 → uint8_t 存不下 → 300 - 256 = 44
```
这和 `& 0xFF`（只取低 8 位）的效果一样。这是 C 语言中利用"无符号整数溢出确定性行为"的技巧，比手动写 `& 0xFF` 更简洁。

### 8.5 le16() —— 小端字节序转换

```c
static inline int16_t le16(uint8_t lo, uint8_t hi)
{
    return (int16_t)(((uint16_t)hi << 8) | (uint16_t)lo);
}
```

**为什么要先转 uint16_t 再移位？**
- `hi` 是 `uint8_t`（8 位），如果直接 `hi << 8`：
  - `uint8_t` 左移 8 位，结果会溢出（8 位最多存 8 位数据）
  - C 语言中，先发生"整型提升"（integer promotion），`uint8_t` 被提升为 `int`，然后左移
  - 但为了清晰和可移植性，**显式转 uint16_t** 更可靠

**小端 vs 大端示例**：
- 数值 `0x1234`（十进制 4660）
- 小端存储：`[0x34, 0x12]` → 拼回去：`(0x12 << 8) | 0x34 = 0x1234` ✅
- 大端存储：`[0x12, 0x34]` → 拼回去：`(0x34 << 8) | 0x12 = 0x3412` ❌（完全不同）

MS901M 和 MSPM0G3507 都是小端，所以直接用 `(hi << 8) | lo`。

### 8.6 sum_bytes() —— 累加和校验

```c
static uint8_t sum_bytes(const uint8_t *data, size_t len)
{
    uint8_t sum = 0u;
    if (data == NULL) { return 0u; }
    for (size_t i = 0u; i < len; ++i) {
        sum = (uint8_t)(sum + data[i]);
    }
    return sum;
}
```

**NULL 检查为什么重要？**
嵌入式系统中，解引用 NULL 指针（访问地址 0）会触发硬件异常（HardFault），导致程序死机。这是最常见的崩溃原因之一。所以对任何传入的指针参数都要做 NULL 检查。

**为什么用 for 循环而不是 while？**
`for (size_t i = 0u; i < len; ++i)` 把"初始化、条件判断、步进"集中在一行，更紧凑。`while` 版本需要三行代码，等效但不够简洁。

### 8.7 set_acc_scale_by_sel() —— 量程映射

```c
static bool set_acc_scale_by_sel(uint8_t fsr)
{
    switch (fsr) {
        case MS901M_ACC_FSR_2G:  s_acc_scale = 2.0f / 32768.0f;  return true;
        case MS901M_ACC_FSR_4G:  s_acc_scale = 4.0f / 32768.0f;  return true;
        case MS901M_ACC_FSR_8G:  s_acc_scale = 8.0f / 32768.0f;  return true;
        case MS901M_ACC_FSR_16G: s_acc_scale = 16.0f / 32768.0f; return true;
        default: return false;
    }
}
```

**switch 和 if-else 的区别**：
- `switch` 适合"多选一"且选项是离散常量的情况
- 编译器通常把 switch 编译成"跳转表"，执行时间是 O(1)
- `if-else if` 链是顺序比较，执行时间是 O(n)

**为什么每个 case 都有 return 而不需要 break？**
`return` 直接结束函数执行，不会继续执行后面的 case。所以不需要 `break`。

### 8.8 build_frame() —— 命令帧构造

```c
static size_t build_frame(uint8_t cmd_id, const uint8_t *data, uint8_t data_len,
    uint8_t *out, size_t out_cap)
{
    size_t frame_len = 5u + (size_t)data_len;
    if (out == NULL || out_cap < frame_len) { return 0u; }
    if (data_len > 0u && data == NULL) { return 0u; }

    out[0] = MS901M_CMD_SYNC1;    // 0x55
    out[1] = MS901M_CMD_SYNC2;    // 0xAF（注意不是 0x55！）
    out[2] = cmd_id;              // 命令 ID
    out[3] = data_len;            // 数据长度
    for (uint8_t i = 0u; i < data_len; ++i) {
        out[4u + i] = data[i];    // 数据内容
    }
    out[frame_len - 1u] = sum_bytes(out, frame_len - 1u);  // 校验和
    return frame_len;
}
```

**数据帧 vs 命令帧的帧头区别**：
| 类型 | 帧头 | 用途 |
|------|------|------|
| 数据帧 | `0x55 0x55` | 传感器→单片机：上报数据 |
| 命令帧 | `0x55 0xAF` | 单片机→传感器：发送命令 |

**为什么用 for 循环拷贝数据，而不是 memcpy()？**
嵌入式开发中，为了减少对外部库函数的依赖，有时选择"手写"循环。`memcpy()` 是 `<string.h>` 中的函数，在某些单片机开发环境中可能不可用或行为不确定。

**缓冲区溢出检查为什么重要？**
检查 `out_cap < frame_len` 防止写入超出缓冲区边界。在嵌入式系统中，缓冲区溢出可能覆盖相邻变量的值，甚至覆盖函数的返回地址，导致程序崩溃或安全漏洞。

### 8.9 ms901m_feed_bytes() —— 核心状态机

这是最核心的函数，是整个模块的"发动机"。它实现了一个**6 状态的有限状态机**。

```
收到的字节        状态变化                     做了什么
────────────────  ──────────                  ──────────
字节 = 0x55       ST_SYNC1 → ST_SYNC2         记下 sum = 0x55
字节 = 0x55       ST_SYNC2 → ST_ID            sum += 0x55
字节 = 0x01       ST_ID → ST_LEN              s_id = 0x01, sum += 0x01
字节 = 0x06       ST_LEN → ST_DATA            s_len = 6, sum += 0x06
字节 = 0x12       ST_DATA(第1个)               s_data[0]=0x12, sum += 0x12
... 收完 6 个后    ST_DATA → ST_CHECKSUM       数据收满
字节 = sum值      ST_CHECKSUM → ST_SYNC1      校验通过！解析 → good++
字节 ≠ sum值      ST_CHECKSUM → ST_SYNC1      校验失败 → bad++
```

**状态机的核心思想**：每个字节到来时，解析器只看两样东西：
1. 当前处于什么状态（`s_state`）
2. 这个字节的值是什么（`b`）

根据这两样决定：
- 要不要保存这个字节
- 下一个状态是什么

这就是"有限状态机"的精华——"当前状态 + 输入 → 下一个状态"。

**为什么需要 ST_SYNC2 状态？**
只用 1 个 0x55 不够可靠——数据内容中也可能出现 0x55。
连续两个 0x55 同时出现的概率大大降低，提高了帧同步的可靠性。

### 8.10 各帧解析函数

**parse_attitude()** —— 最关键的解析函数：
```c
s_snap.pitch_deg = (float)le16(d[2], d[3]) * (180.0f / 32768.0f);
```
- `le16(d[2], d[3])`：把两个字节合成 int16 原始值
- `(float)`：强转为浮点数，避免整数运算
- `* (180.0f / 32768.0f)`：乘以换算系数 ≈ 0.005493
- 结果存入 `s_snap.pitch_deg`，平衡控制算法直接使用

**换算系数推导**：MS901M 的姿态角输出范围是 -180°~+180°，对应 int16 的 -32768~+32767。所以 1 个 LSB = 180°/32768。

**parse_gyro_acc()** —— 提供角速度：
```c
s_snap.gy_dps = (float)le16(d[8], d[9]) * s_gyro_scale;
```
`gy_dps` = Y 轴角速度 = 俯仰角速度（pitch_rate），是 PD 控制器的 **D 项**输入。

**parse_mag_temp()** —— 只取温度：
磁力计数据（d[0]~d[5]）被故意忽略，因为电机 PWM 的强电磁场会严重干扰磁力计读数。温度数据保留，用于可能的温漂补偿。

### 8.11 便捷命令函数

```c
size_t ms901m_build_save_cmd(uint8_t *out, size_t out_cap)
{
    return ms901m_build_write_u8_cmd(MS901M_CMD_SAVE, 0x00u, out, out_cap);
}
```

这个函数只有一行，直接调用了 `ms901m_build_write_u8_cmd()`。它存在的意义是"给有名字的命令配上专用的函数"——调用方不需要知道 SAVE 的命令 ID 是 0x00，只需要调用 `ms901m_build_save_cmd()`。

这种"封装"设计模式在嵌入式驱动中很常见，提高代码的可读性和易用性。

### 9.1 static 关键字

| **static 全局变量** | `static uint8_t s_chk = 0u;` | 变量只在当前文件可见，其他 .c 文件无法访问 |

**为什么用 s_ 前缀？**
这是命名惯例——`s_` 表示 "static"，提醒读者"这是一个模块内部静态变量"。

### 9.2 uint8_t / int16_t / uint32_t 等定宽类型

来自 `<stdint.h>` 头文件，保证了**在所有平台上长度一致**：
| 类型 | 长度 | 范围 |
|------|------|------|
| `uint8_t` | 8 位无符号 | 0 ~ 255 |
| `int16_t` | 16 位有符号 | -32768 ~ 32767 |
| `uint32_t` | 32 位无符号 | 0 ~ 4294967295 |

相比 `int`（不同平台长度不同），定宽类型更适合嵌入式开发和通信协议编程。

### 9.3 size_t 类型

`size_t` 是 `sizeof` 运算符返回的无符号整数类型，通常定义为 `unsigned int` 或 `unsigned long`。在 32 位系统上是 32 位，64 位系统上是 64 位。

使用场景：表示"字节数"或"数组长度"。

### 9.4 inline 关键字

```c
static inline int16_t le16(uint8_t lo, uint8_t hi)
```

`inline` 建议编译器把函数体直接嵌入调用处，避免函数调用（压栈/跳转/出栈）的开销。对于 `le16()` 这种只有一行 return 的"小函数"特别合适。

但 `inline` 只是"建议"——编译器可以忽略。最终的优化决策由编译器根据代码大小和速度权衡。

### 9.5 三元运算符

```c
s_state = (s_len == 0u) ? ST_CHECKSUM : ST_DATA;
```

等价于：
```c
if (s_len == 0u) {
    s_state = ST_CHECKSUM;
} else {
    s_state = ST_DATA;
}
```

三元运算符让简单的条件赋值在一行内完成，更紧凑。但嵌套使用会降低可读性，建议只用于简单场景。

### 9.6 (void) 消除未使用参数警告

```c
static void parse_quaternion(const uint8_t *d, uint8_t len)
{
    (void)d;  // 告诉编译器"我故意不用参数 d"
    if (len != 8u) { return; }
}
```

`(void)d;` 生成一条"把 d 的值读入但不用"的代码，编译器看到"参数被使用了"，就不会产生 warning。这是嵌入式开发中常见的"消除警告"技巧。

### 9.7 整数除法陷阱

```c
// 错误的写法（整数除法）：
float bad = 4 / 32768;    // 结果 = 0.0f！（因为 4 ÷ 32768 = 0，整数除法舍去小数）

// 正确的写法（浮点除法）：
float good = 4.0f / 32768.0f;  // 结果 = 0.000122f
```

C 语言中，两个整数相除结果还是整数，小数部分被直接截断。只要有一个操作数是浮点数，就执行浮点除法。

## ⚡ 十一、平衡控制与 ms901m 模块的关系

### 11.1 PD 控制器需要什么数据？

平衡控制的核心思想：**让小车保持直立 → 让 pitch 角保持为 0°**

| 控制器项 | 物理量 | 数据来源 | 在 ms901m 中的字段 |
|---------|--------|---------|-------------------|
| P（比例） | 当前俯仰角 | 0x01 帧姿态数据 | `snap.pitch_deg` |
| D（微分） | 俯仰角速度 | 0x03 帧陀螺数据 | `snap.gy_dps` |

### 11.2 PD 控制器的简化公式

```
电机输出 = Kp × pitch + Kd × pitch_rate
其中：
  pitch      = snap.pitch_deg    （当前偏离直立的程度）
  pitch_rate = snap.gy_dps       （当前倾倒的速度）
  Kp         = 比例增益系数       （越大纠正越猛）
  Kd         = 微分增益系数       （越大刹车越强）
```

- **P 项**：pitch 越大（倒得越厉害），电机出力越大，把车体推回直立
- **D 项**：pitch_rate 越大（倒得越快），电机出反向力，"刹车"防止冲过头
- 没有 D 项 → 小车会来回震荡（就像只有弹簧没有阻尼器）

### 11.3 为什么需要 200 Hz 的更新率？

自平衡小车的自然振荡频率通常在几个 Hz 到十几 Hz。根据"奈奎斯特采样定理"，控制频率至少是系统最高频率的 2 倍，实际工程中通常取 **5~10 倍**。

200 Hz（每 5 ms 一次）对于平衡控制来说是充足的。如果降到 50 Hz，控制延迟变大，小车可能会抖或倒。

### 11.4 量程选择对控制的影响

| 量程 | 精度 | 适用场景 |
|------|------|---------|
| ±2g | 最高 (0.061 mg/LSB) | 静态倾角测量 |
| ±4g | 高 (0.122 mg/LSB) | 自平衡推荐，出厂默认 |
| ±8g | 中等 (0.244 mg/LSB) | 运动较剧烈时 |
| ±16g | 低 (0.488 mg/LSB) | 剧烈运动、碰撞检测 |

选择量程是"精度 vs 范围"的权衡。自平衡小车推荐 ±4g 或 ±8g。

## 🐛 十二、常见错误与调试方法

### 12.1 调试日志输出建议

在 `app_telemetry.c` 中，建议定期（如每 1 秒）输出以下信息：

```
[IMU] good=5230 bad=2 pitch=+1.2° rate=-3.4°/s temp=25.3°C
```

解读：
- `good=5230`：已成功接收 5230 帧，通信正常
- `bad=2`：只有 2 帧校验失败，通信质量良好
- `pitch=+1.2°`：当前俯仰角，接近 0° 说明小车直立
- `rate=-3.4°/s`：当前俯仰角速度，小值正常

### 12.2 常见问题排查表

| 现象 | 可能原因 | 排查方法 |
|------|---------|---------|
| `has_attitude` 一直 false | 1. MS901M 没上电<br>2. UART 引脚接错<br>3. 波特率不匹配<br>4. MS901M 坏了 | 1. 测 MS901M 电源引脚电压<br>2. 用示波器看 TX 引脚有无波形<br>3. 换不同波特率试 |
| `bad_frames` 快速增长 | 1. 波特率不匹配（最常见）<br>2. 串口线受 PWM 电机干扰<br>3. 共地问题 | 1. 确认两边波特率一致<br>2. 串口线远离电机线<br>3. 检查共地 |
| pitch 值偏大/偏小 | `ms901m_init()` 量程参数不对 | 用 ATK 上位机查看当前配置 |
| pitch 有值但不变化 | 传感器固定不牢固，随车体一起晃 | 检查传感器安装 |
| pitch 跳变剧烈 | 串口数据偶尔错位，状态机同步到错误帧头 | 检查 `bad_frames` 是否太高 |

### 12.3 使用 VOFA+ 调试

项目中的 `vofa.h/c` 模块提供了串口数据可视化支持。配合 VOFA+ 上位机，可以实时看到 pitch 和 rate 的波形曲线，对调试平衡参数非常有帮助。

```
main循环中：
  vofa_send(pitch, rate, motor_output);
  → 电脑端的 VOFA+ 显示三条实时曲线
```

## 📖 十三、扩展阅读

### 13.1 什么是惯性测量单元（IMU）？

IMU = Inertial Measurement Unit，惯性测量单元，包含：
- **加速度计**：测量加速度（包括重力加速度），3 轴输出
- **陀螺仪**：测量角速度（旋转速度），3 轴输出

MS901M 还额外包含磁力计和气压计，以及一颗专门做数据融合的 MCU。

### 13.2 什么是姿态解算？

姿态解算 = 把陀螺仪和加速度计的原始数据融合成有意义的姿态角。

**陀螺仪的问题**：短时间准，但积分会漂移（误差累积）
**加速度计的问题**：长时间稳，但有振动时噪声大

**融合方法**：
1. **互补滤波**：简单，适合资源受限的 MCU
2. **Mahony 滤波**：中等复杂度，效果不错
3. **卡尔曼滤波**：最精确，但计算量大

MS901M 内部自带十五阶卡尔曼滤波器，直接输出融合后的姿态角——所以我们不需要在 MSPM0G3507 上做姿态解算，直接读角度即可。

### 13.3 什么是 UART？

UART = Universal Asynchronous Receiver/Transmitter，通用异步收发器

特点：
- **异步**：不需要时钟线，发送方和接收方各自用自己的时钟
- **全双工**：可以同时发送和接收
- **需要约定波特率**：双方必须用相同的速率通信

**波特率** = 每秒传输的位数（bps）。115200 bps 意味着每秒传输约 11520 字节（115200/10，每字节 8 位数据 + 1 位起始 + 1 位停止）。

### 13.4 什么是环形缓冲区（Ring Buffer）？

环形缓冲区是一种"先进先出"的数据结构，用固定大小的数组实现循环利用：
- 写指针：ISR 往缓冲区写数据时移动
- 读指针：主循环从缓冲区读数据时移动
- 当写指针追上读指针 → 缓冲区满（新数据覆盖旧数据或丢弃）

这种设计让中断处理非常快（只需移动指针+写几个字节），而大量数据处理推迟到主循环中做。

### 13.5 int16 的范围为什么是 -32768 ~ +32767？

16 位有符号整数用"补码"表示：
- 正数：0x0001 ~ 0x7FFF → 1 ~ 32767
- 零： 0x0000 → 0
- 负数：0xFFFF ~ 0x8000 → -1 ~ -32768

所以 int16 能表示的总数是 65536 个（2^16），范围从 -32768 到 +32767。
