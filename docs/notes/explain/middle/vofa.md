# VOFA+ 数据可视化模块 学习笔记

## 📖 一、整体概述

### 1.1 这个模块在项目中的位置

本项目是一个**两轮自平衡瞄准小车**，主控为 **TI MSPM0G3507**。

在调试阶段，我们需要实时查看小车的运行数据——俯仰角、角速度、电机输出等。
通过 VOFA+ 模块，这些数据被发送到电脑上，绘制成实时波形曲线，
让调试变得直观而高效。

```
┌──────────────────────────────────────────────────────────┐
│                    app_telemetry.c                        │  ← 应用层：遥测数据上报
│  每 50 ms 调用一次 vofa_send() 发送 pitch/rate/output     │
└────────────────────┬─────────────────────────────────────┘
                     │ float 数组
┌────────────────────▼─────────────────────────────────────┐
│                   vofa.h / vofa.c                         │  ← 中间层：本模块
│            JustFloat 协议打包 + 函数指针注入式发送          │
└────────────────────┬─────────────────────────────────────┘
                     │ 字节流
┌────────────────────▼─────────────────────────────────────┐
│             bsp_log_uart.c / 蓝牙 UART                     │  ← 硬件驱动层
│             通过串口把字节发送到电脑                        │
└──────────────────────────────────────────────────────────┘
                     │ USB 线 / 蓝牙
┌────────────────────▼─────────────────────────────────────┐
│              电脑上的 VOFA+ 上位机                         │  ← 可视化工具
│              实时绘制波形曲线，观察数据趋势                 │
└──────────────────────────────────────────────────────────┘
```

### 1.2 什么是 VOFA+？

VOFA+ 是一款免费的**串口数据可视化工具**（上位机软件）。

**没有 VOFA+ 时的调试方式**：看串口打印的文本数字
```
pitch=1.23, rate=-4.56, output=57.80
pitch=1.25, rate=-4.51, output=57.50
pitch=1.20, rate=-4.62, output=58.10
...
```
——满屏滚动的数字，很难看出趋势。

**有 VOFA+ 时的调试方式**：看实时波形曲线
```
pitch ────╮  ╰╮  ╰──╮  ╭──╮  ╭─
rate  ────╯   ╰───╯   ╰──╯  ╰──
output ──╮ ╭─╯ ╭─╯ ╭─╯ ╭─╯ ╭─
```
——三条曲线一目了然：pitch 震荡了、rate 超调了、output 饱和了。

### 3.2 JustFloat 协议详解

JustFloat 协议是 VOFA+ 支持的一种**二进制协议**。

#### 数据格式

```
┌──────────┬──────────┬──────────┬──────────┐
│  ch[0]   │  ch[1]   │  ch[2]   │  帧尾     │
│  4 字节   │  4 字节  │  4 字节  │  4 字节   │
│ (float)  │ (float)  │ (float)  │ (固定值)  │
└──────────┴──────────┴──────────┴──────────┘
├────────── 16 字节 ──────────────────────┤
```

#### 帧尾的奥秘

帧尾 = 0x00 0x00 0x80 0x7F

这 4 个字节恰好是 IEEE 754 浮点数的 **+infinity（正无穷）** 的小端表示：

```
IEEE 754 32-bit float 的 +infinity 二进制 = 0 11111111 00000000000000000000000
                                           ↑  ↑        ↑
                                         符号 指数(全1)  尾数(全0)
                                        = 0x7F800000（大端）

小端存储（低地址存低字节）：
  低地址 → 0x00 0x00 0x80 0x7F → 高地址
```

**为什么用 +inf 做帧尾？**
因为正常的 float 数据**不可能是正无穷**（NaN 也不可能），所以 VOFA+ 协议设计者选择了 +inf 的字节序列作为"帧结束标记"。这是一种"带外标识"（sentinel value）技术——用不可能出现在数据中的特殊值来标记边界。

**帧尾的工作方式：**
1. VOFA+ 不断从串口接收字节
2. 每收到一个字节，就检查是否匹配帧尾序列
3. 如果匹配到了帧尾，就把之前收到的所有 float 解析为一帧
4. 然后清空缓冲区，开始接收下一帧

#### 为什么不用文本协议？

文本协议（如 CSV 格式）：
```
1.23, -4.56, 57.80\n
```

| 特性 | 文本协议（CSV） | 二进制协议（JustFloat） |
|------|---------------|----------------------|
| 数据量 | 每个 float 约 8~15 字节 | 每个 float 固定 4 字节 |
| 解析难度 | 需要字符串分割、转换 | 直接 memcpy |
| 浮点精度 | 受文本转浮点精度损失 | 无精度损失 |
| 人眼可读 | 是 | 否 |
| 适用场景 | 偶尔看一下 | 实时高频波形显示 |

自平衡小车的控制频率是 200 Hz，数据量大，用二进制协议更高效。

### 3.3 函数指针注入设计

```c
typedef void (*vofa_writer_fn)(const uint8_t *data, size_t len);
```

**为什么使用函数指针而不是直接调用 UART 函数？**

如果 vofa_send() 直接调用某个具体的 UART 发送函数，比如：
```c
void vofa_send(...) {
    // 直接调用 UART1 的发送函数
    uart1_send_bytes(buf, len);
}
```

那么当你想切换输出路径时（比如从 USB 串口切换到蓝牙），就需要修改 vofa.c 的代码。这破坏了"开闭原则"——对扩展开放，对修改关闭。

**函数指针注入的解决方案**：
```c
// 初始化时注册写函数
vofa_set_writer(uart1_send_bytes);   // 用 USB 串口
// 之后想换蓝牙，改一行
vofa_set_writer(bluetooth_send_bytes); // 用蓝牙

// vofa_send() 内部调用注册的函数
void vofa_send(...) {
    ...
    s_writer(buf, len);  // 调用注册的函数，不管它是哪个
}
```

这样就可以在不修改 vofa.c 的情况下切换输出路径。

## 🧩 四、vofa.c 代码逐段详解

### 4.1 头文件包含

```c
#include "vofa.h"
#include <string.h>
```

`#include <string.h>` 引入了 `memcpy` 函数。在 vofa_send() 中，用 `memcpy` 把 float 数组和帧尾拷贝到栈上缓冲区，而不是逐字节赋值。

**为什么用 memcpy 而不是 for 循环？**
- `memcpy` 通常被编译器优化为"块拷贝指令"（如 ARM 的 LDM/STM），比 for 循环快
- 代码更简洁——三行 vs 一个循环
- 注意：在 Keil MDK 中，`memcpy` 可能会被展开为 `__aeabi_memcpy`，性能比手写循环好

### 4.2 常量与静态变量

```c
#define VOFA_MAX_CHANNELS  32u

static const uint8_t JUSTFLOAT_TAIL[4] = { 0x00u, 0x00u, 0x80u, 0x7Fu };
static vofa_writer_fn s_writer = NULL;
```

**`VOFA_MAX_CHANNELS = 32`**：这个值决定了 vofa_send() 内部栈上缓冲区的大小。缓冲区大小 = 32 × 4 + 4 = 132 字节。对于 MSPM0G3507（32 KB RAM 版本），132 字节的栈上分配非常安全。

**`static const` 修饰 JUSTFLOAT_TAIL**：
- `static`：只在当前文件可见
- `const`：内容不可修改，放在 ROM（Flash）中，不占 RAM
- 在嵌入式系统中，能用 `const` 就尽量用——宝贵的 RAM 应该留给变量

**`s_writer = NULL`**：初始化为 NULL，这样如果忘记调用 `vofa_set_writer()`，`vofa_send()` 会因为 `s_writer == NULL` 而安全返回，不会崩溃。

### 4.3 vofa_set_writer() —— 注册写函数

```c
void vofa_set_writer(vofa_writer_fn writer)
{
    s_writer = writer;
}
```

这个函数简单到只有一行赋值——但它体现了"依赖注入"（Dependency Injection）设计模式。

**依赖注入**：模块不自己创建依赖，而是由外部"注入"进来。

对比不使用依赖注入的写法：
```c
// 不使用依赖注入：vofa.c 直接调用硬件函数
void vofa_send(...) {
    uart1_send_bytes(buf, len);  // 硬编码依赖
}
```

使用依赖注入的写法：
```c
// 使用依赖注入：vofa.c 通过函数指针调用
void vofa_send(...) {
    s_writer(buf, len);  // 依赖由外部注入
}
```

### 4.4 vofa_send() ⭐ —— 核心打包发送函数

```c
void vofa_send(const float *ch, uint8_t n)
{
    if (s_writer == NULL || ch == NULL) { return; }
    if (n == 0u || n > VOFA_MAX_CHANNELS) { return; }

    uint8_t buf[VOFA_MAX_CHANNELS * 4u + 4u];
    size_t  payload_bytes = (size_t)n * sizeof(float);
    memcpy(buf, ch, payload_bytes);
    memcpy(&buf[payload_bytes], JUSTFLOAT_TAIL, 4u);

    s_writer(buf, payload_bytes + 4u);
}
```

#### 第 1~2 行：安全检查

```c
if (s_writer == NULL || ch == NULL) { return; }
if (n == 0u || n > VOFA_MAX_CHANNELS) { return; }
```

四个条件，分别对应四种异常情况：

| 条件 | 含义 | 后果如果不检查 |
|------|------|--------------|
| `s_writer == NULL` | 忘记注册写函数 | `s_writer(buf, len)` 会调用地址 0 → 死机 |
| `ch == NULL` | 传入空指针 | `memcpy(buf, NULL, n)` → 死机 |
| `n == 0` | 没有数据要发送 | 浪费一次函数调用，无害但多余 |
| `n > 32` | 通道数超出上限 | `buf` 只有 132 字节，`memcpy` 会写越界 |

#### 第 4 行：栈上缓冲区

```c
uint8_t buf[VOFA_MAX_CHANNELS * 4u + 4u];
```

在栈上分配一个固定大小的数组。`32 × 4 + 4 = 132` 字节。

**为什么不动态分配（malloc）？**
嵌入式系统中**禁止使用 malloc**，原因：
1. 内存碎片——反复分配释放会产生无法利用的小碎片
2. 分配失败——单片机没有虚拟内存，malloc 可能返回 NULL
3. 不确定性——malloc 的执行时间不确定，影响实时性

所以嵌入式程序通常使用**静态分配**或**栈上分配**。

**132 字节在栈上安全吗？**
MSPM0G3507 的栈大小通常在 1~4 KB（在启动文件中配置）。132 字节约占 3%~13%，非常安全。

#### 第 5 行：计算数据长度

```c
size_t payload_bytes = (size_t)n * sizeof(float);
```

`sizeof(float)` 在 C 标准中保证为 4 字节（IEEE 754 单精度）。

`(size_t)n` 把 `uint8_t` 提升为 `size_t`，避免乘法溢出。虽然 n 最大 32，32 × 4 = 128 不会溢出 uint8_t，但这是一个好习惯。

#### 第 6~7 行：拷贝数据到缓冲区

```c
memcpy(buf, ch, payload_bytes);
memcpy(&buf[payload_bytes], JUSTFLOAT_TAIL, 4u);
```

**第一次 memcpy**：把 n 个 float 的二进制表示原样拷贝到 buf 中。

**第二次 memcpy**：把 4 字节帧尾追加到 float 数据的后面。

`&buf[payload_bytes]` 是指向"float 数据末尾"的指针。例如 n=3 时，payload_bytes=12，帧尾从 buf[12] 开始存放。

#### 第 9 行：一次发送

```c
s_writer(buf, payload_bytes + 4u);
```

调用注册的 writer 函数，一次性发送所有字节。

**为什么一次发送而不是逐 float 发送？**
假设串口每次发送都需要中断处理，一次发 16 字节 vs 发 4 次每次 4 字节：
- 一次发：1 次中断
- 分 4 次发：4 次中断

中断多了会占用 CPU 时间，影响控制循环的实时性。

### 4.5 完整的内存布局示例

假设 `n = 3`，`ch = [1.5f, -2.0f, 100.0f]`：

```
buf 数组内容（共 16 字节）：
┌─────────────────────────────────────────────────────────────────┐
│ 偏移 0~3:   ch[0] = 1.5f 的 IEEE 754 表示                     │
│             0x3FC00000 (大端) → [0x00, 0x00, 0xC0, 0x3F] (小端)│
├─────────────────────────────────────────────────────────────────┤
│ 偏移 4~7:   ch[1] = -2.0f 的 IEEE 754 表示                    │
│             0xC0000000 (大端) → [0x00, 0x00, 0x00, 0xC0] (小端)│
├─────────────────────────────────────────────────────────────────┤
│ 偏移 8~11:  ch[2] = 100.0f 的 IEEE 754 表示                   │
│             0x42C80000 (大端) → [0x00, 0x00, 0xC8, 0x42] (小端)│
├─────────────────────────────────────────────────────────────────┤
│ 偏移 12~15: JUSTFLOAT_TAIL = [0x00, 0x00, 0x80, 0x7F]         │

```

### 4.6 从代码注释中提炼的额外设计细节

**为什么使用固定大小缓冲区而不是 VLA（变长数组）？**
理论上可以写成 `uint8_t buf[n * 4 + 4]` 来按需分配。但：
1. VLA 在 C99 标准中可用，但在嵌入式 C 编译器中支持不一
2. VLA 如果 n 意外变得很大，可能导致栈溢出（stack overflow）
3. 固定大小 `[132]` 的分配时间是完全确定的——只是移动栈指针

**为什么分两次 memcpy 而不是一次？**
可以合成一次：先 memcpy float 数据，再 memcpy 帧尾。分开写的优点是代码意图更清晰——读者一眼就能看出"先拷贝数据，再追加帧尾"。编译器通常会合并这两个相邻的 memcpy 调用。

**为什么 s_writer 初始化为 NULL？**
这是"默认安全"设计。如果调用方忘记调用 `vofa_set_writer()`，`s_writer` 保持 NULL，`vofa_send()` 会检测到并安全返回，不会调用地址 0。这比没有初始值（随机地址）安全得多。

### 4.7 vofa.c 的代码设计模式总结

| 设计模式 | 体现位置 | 说明 |
|---------|---------|------|
| **防御性编程** | `vofa_send()` 开头的 4 个检查 | 所有异常输入都被拦截，不会崩溃 |
| **依赖注入** | `vofa_set_writer()` + `s_writer` 函数指针 | vofa 模块不依赖具体 UART，由外部注入 |
| **栈上分配** | `uint8_t buf[132]` | 不使用 malloc，适合单片机 |
| **批量处理** | 一次 memcpy 全部 float + 一次发送 | 减少函数调用次数和中断次数 |
| **哨兵值** | JUSTFLOAT_TAIL = +inf 的字节序列 | 用不可能出现的值标记帧边界 |
| **静态封装** | `static` 变量和 `static const` 数组 | 内部实现对外部隐藏 |

## 🔍 五、C 语言关键语法知识点

### 5.1 函数指针

```c
typedef void (*vofa_writer_fn)(const uint8_t *data, size_t len);
```

**语法解析**（从内向外读）：
1. `(*vofa_writer_fn)`：`vofa_writer_fn` 是一个指针
2. `(*vofa_writer_fn)(...)`：这个指针指向一个函数
3. `void (*vofa_writer_fn)(...)`：这个函数返回 void（无返回值）
4. `(const uint8_t *data, size_t len)`：函数接受两个参数

**使用函数指针的步骤**：
```c
// 1. 定义符合签名（signature）的函数
void my_uart_sender(const uint8_t *data, size_t len) {
    uart_send(data, len);
}

// 2. 注册为 writer
vofa_set_writer(my_uart_sender);
// 等价于：把 my_uart_sender 的函数地址赋值给 s_writer

// 3. vofa_send 内部调用（不需要知道具体是哪个函数）
s_writer(buf, len);
// 等价于：my_uart_sender(buf, len)
```

**函数指针的典型应用场景**：
- 回调函数（Callback）：如本模块的 writer
- 策略模式（Strategy Pattern）：运行时切换算法
- 中断服务程序注册
- 状态机中的动作表

### 5.2 static const 组合

```c
static const uint8_t JUSTFLOAT_TAIL[4] = { 0x00u, 0x00u, 0x80u, 0x7Fu };
```

`static` + `const` 是一个强大的组合：

| 关键字 | 作用 | 效果 |
|--------|------|------|
| `static` | 链接属性 | 只在当前文件可见，其他 .c 文件不能访问 |
| `const` | 类型属性 | 内容不可修改，放在 ROM（Flash）中 |

在嵌入式系统中，`static const` 数组不会占用 RAM，而是被编译器放在 Flash 的只读数据段（.rodata）。这对于资源受限的单片机非常重要。

### 5.3 memcpy 的使用场景

```c
#include <string.h>

memcpy(buf, ch, payload_bytes);
memcpy(&buf[payload_bytes], JUSTFLOAT_TAIL, 4u);
```

`memcpy` 是 C 标准库中最常用的内存操作函数之一。

**memcpy 的特点**：
- 从源地址拷贝 n 个字节到目标地址
- 源和目的不能重叠（重叠用 memmove）
- 对于小数据量（几十字节），编译器通常会内联优化

**memcpy 的替代方案**：
```c
// 方案 1：for 循环（不依赖标准库）
for (size_t i = 0; i < payload_bytes; i++) {
    buf[i] = ((const uint8_t*)ch)[i];
}

// 方案 2：memcpy（依赖 <string.h>）
memcpy(buf, ch, payload_bytes);
```

方案 1 更"自包含"，但代码冗长。方案 2 更简洁，且可能被优化得更快。在 Keil MDK 中，`memcpy` 通常会被优化为高效的块拷贝指令。

### 5.4 sizeof 运算符

```c
size_t payload_bytes = (size_t)n * sizeof(float);
```

`sizeof(float)` 在编译时求值，结果为 4（float 占 4 字节）。它不是一个函数调用，而是一个**编译时运算符**——在编译阶段就确定了值，运行时零开销。

常见类型的 sizeof：
| 类型 | sizeof 结果 | 说明 |
|------|------------|------|
| `char` / `uint8_t` | 1 | 字节 |
| `int16_t` / `short` | 2 | 半字 |
| `float` / `int32_t` | 4 | 字 |
| `double` | 8 | 双字 |

### 5.5 函数指针 vs 直接函数调用

```c
// 方式 A：直接函数调用（硬编码）
void vofa_send(...) {
    uart1_send_bytes(buf, len);
}

// 方式 B：函数指针调用（注入）
void vofa_send(...) {
    s_writer(buf, len);
}
```

| 特性 | 方式 A（直接调用） | 方式 B（函数指针） |
|------|-------------------|-------------------|
| 耦合度 | 高（依赖具体模块） | 低（依赖抽象接口） |
| 灵活性 | 低（改功能要改代码） | 高（运行时切换） |
| 性能 | 高（直接跳转） | 略低（间接跳转） |
| 可测试性 | 低（难模拟） | 高（可注入假函数） |

在嵌入式系统中，性能差异通常可以忽略——函数指针的间接调用只多了一条指令。

## ⚡ 六、在项目中的实际使用

### 6.1 典型使用场景

```c
// 在 main.c 或 app_telemetry.c 中

#include "vofa.h"
#include "bsp_log_uart.h"  // 日志串口驱动

int main(void) {
    // 初始化...
    bsp_log_uart_init(115200);
    
    // 注册 VOFA+ 的 writer 为日志串口发送函数
    vofa_set_writer(bsp_log_uart_send_bytes);
    
    // 主循环
    for (;;) {
        // ... 平衡控制 ...
        
        // 每 50 ms 发一次数据到 VOFA+
        if (telemetry_timer >= 50) {
            float channels[4];
            channels[0] = snap.pitch_deg;   // 俯仰角
            channels[1] = snap.gy_dps;      // 角速度
            channels[2] = motor_output;     // 电机输出
            channels[3] = battery_voltage;  // 电池电压
            
            vofa_send(channels, 4);
            telemetry_timer = 0;
        }
    }
}
```

### 6.2 VOFA+ 上位机设置

在电脑上操作 VOFA+：
1. 打开 VOFA+ 软件
2. 点击左上角的"串口"按钮
3. 选择正确的串口号（与单片机相连的端口）
4. 设置波特率（与单片机 UART 配置一致，如 115200）
5. 在协议选择中选 **"JustFloat"**
6. 设置通道数 = 4（与 vofa_send(channels, 4) 中的 4 对应）
7. 点击"开始"
8. 此时应该能看到 4 条波形曲线

### 6.3 蓝牙无线调试

如果使用蓝牙串口模块（如 HC-05/HC-06）：
```c
// 初始化蓝牙串口
bsp_bluetooth_uart_init(115200);

// 注册 VOFA+ writer 为蓝牙发送函数
vofa_set_writer(bsp_bluetooth_uart_send_bytes);

// 现在可以通过蓝牙无线查看波形了！
```

## 📊 七、VOFA+ 数据调试技巧

### 7.1 常见调试通道配置

| 调试目的 | 通道数 | 通道内容 |
|---------|--------|---------|
| 平衡环调参 | 3 | pitch, pitch_rate, motor_output |
| 速度环调参 | 3 | velocity_target, velocity_actual, motor_output |
| 循迹调试 | 4 | track_error, phase_angle, v_cmd, omega_cmd |
| 云台瞄准 | 3 | laser_dx, laser_dy, pitch_feedforward |
| 电池续航 | 2 | battery_voltage, current_consumption |
| 全量监测 | 6 | pitch, rate, motor, battery, laser_dx, laser_dy |

### 7.2 发送频率的选择

| 频率 | 间隔 | 适用场景 |
|------|------|---------|
| 10 Hz | 100 ms | 观察缓慢变化（电池电压、温度） |
| 20 Hz | 50 ms | 通用的调试频率（推荐） |
| 50 Hz | 20 ms | 观察快速变化（平衡震荡） |
| 100 Hz | 10 ms | 高频调试，注意串口带宽 |

**注意串口带宽**：
- 假设用 115200 bps，每秒最大传输 ~11520 字节
- 4 通道：每帧 = 4×4 + 4 = 20 字节
- 20 Hz 时：20 × 20 = 400 字节/秒，占带宽 3.5%，非常宽裕
- 100 Hz 时：100 × 20 = 2000 字节/秒，占带宽 17%，仍可接受

### 7.3 波形分析方法

```
波形 1：平衡环正在震荡（Kp 太大或 Kd 太小）
  pitch ━┳━┳━┳━┳━┳━┳━┳━┳━┳━┳━┳━┳━  (等幅震荡)
  rate  ━┻━┻━┻━┻━┻━┻━┻━┻━┻━┻━┻━┻━

波形 2：平衡环已稳定（良好的调参结果）
  pitch ━━━━━━━━━━━━━━━━━━━━━━━━━  (接近 0)
  rate  ━━━━━━━━━━━━━━━━━━━━━━━━━  (接近 0)

波形 3：有静差（Ki 不够）
  pitch ━━━━━━━━━╮━━━━━━━━━╮━━━━━  (始终偏一个固定值)
                  ╰━━━━━━━━╯        (试图回正但回不到 0)

波形 4：积分饱和（Ki 太大）
  pitch ━━╮  ╰━━╮  ╰━━╮  ╰━━╮     (超调严重)
  motor ━━╮  ╰━━╮  ╰━━╮  ╰━━╮     (输出一直顶到上限)
```

## 🐛 八、常见错误与调试方法

### 8.1 常见问题排查

| 现象 | 可能原因 | 解决方法 |
|------|---------|---------|
| VOFA+ 没有波形 | 忘记调用 `vofa_set_writer()` | 检查初始化代码 |
| 波形不动 | VOFA+ 协议选错 | 选择 "JustFloat" |
| 波形乱跳 | 帧尾损坏 | 检查 JUSTFLOAT_TAIL 是否被修改 |
| 波形延迟大 | 发送频率太低 | 提高调用 `vofa_send()` 的频率 |
| 波形断断续续 | 串口缓冲区溢出 | 降低发送频率或提高波特率 |
| 数据全是 0 | ch 数组未赋值 | 检查 ch 数组是否有有效数据 |

### 8.2 常见错误场景

**场景 1：忘记注册 writer**
```c
// ❌ 错误：只调用了 vofa_send，没有先调 vofa_set_writer
vofa_send(channels, 3);  // s_writer == NULL → 静默返回，什么都不发
```

**场景 2：通道数不匹配**
```c
// ❌ 错误：发送 3 个通道，但 VOFA+ 设了 4 个通道
vofa_send(channels, 3);  // 发 3 个 float + 帧尾 = 16 字节
// VOFA+ 解析时以为有 4 个通道，但数据不够 → 等待下一帧 → 错位
```

**场景 3：发送频率过高**
```c
// ❌ 错误：每 1 ms 发一帧，远远超出串口带宽
// 115200 bps ÷ (4×4+4)×8 = 115200 ÷ 160 = 720 帧/秒
// 但实际上串口加上中断开销，不可能达到 1000 Hz 的稳定发送
```

**场景 4：缓冲区溢出**
```c
// ❌ 错误：通道数超过 32
float big_data[64];
vofa_send(big_data, 64);  // n > 32 → 被 return 拦截，数据丢失
```

### 8.3 使用示波器调试波形

如果 VOFA+ 完全没有数据，先用串口助手（如 SSCOM、Putty）验证：
1. 不用 VOFA+，改用串口助手接收
2. 看看是否能收到原始二进制数据
3. 如果能收到（看到乱码），说明 UART 通信正常，问题在 VOFA+ 配置
4. 如果收不到，说明 UART 硬件或驱动有问题

## 📖 九、扩展阅读

### 9.1 什么是 IEEE 754 浮点数？

IEEE 754 是计算机浮点数的国际标准。32 位 float 的布局：

```
31 30    23 22                    0
├─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┼─┤
│S│  指数（8位）  │              尾数（23位）                       │
└─┴───────────────┴───────────────────────────────────────────────┘
```

- S（1 bit）：符号位，0=正，1=负
- 指数（8 bits）：以偏移 127 的方式表示（实际值 = 存储值 - 127）
- 尾数（23 bits）：表示 1.xxxxx 的小数部分

**特殊值**：
| 符号 | 指数 | 尾数 | 含义 |
|------|------|------|------|
| 0 | 全 1 (0xFF) | 全 0 | +infinity（正无穷） |
| 1 | 全 1 (0xFF) | 全 0 | -infinity（负无穷） |
| 0/1 | 全 1 (0xFF) | 非 0 | NaN（不是一个数） |

**+infinity 的字节序列**：
- 大端：`0x7F 0x80 0x00 0x00`
- 小端：`0x00 0x00 0x80 0x7F` ← 这就是 JUSTFLOAT_TAIL！

### 9.2 什么是小端（Little-Endian）？

Endianness（字节序）描述了多字节数据在内存中的排列顺序。

```
存储 int32 值 0x12345678（十进制 305419896）：

小端（Little-Endian，MSPM0G3507 使用）：
  低地址 → [0x78] [0x56] [0x34] [0x12] → 高地址
             低字节    高字节

大端（Big-Endian，网络字节序）：
  低地址 → [0x12] [0x34] [0x56] [0x78] → 高地址
             高字节    低字节
```

JustFloat 协议要求**小端**格式。MSPM0G3507 是 Cortex-M0+ 内核，使用小端模式，所以 float 数据无需做字节序转换直接发送即可。如果移植到大端单片机，需要在 `vofa_send` 中先转换字节序再发送。

### 9.3 什么是回调函数（Callback）？

回调函数是一种"你叫我，我回头再叫你"的编程模式。

**生活类比**：
你（单片机）想订外卖（发数据），但你不知道外卖小哥（UART）的电话。
于是你告诉前台（vofa 模块）："送外卖的来了，让他送到 301 房间。"
前台记住了。外卖来了，前台直接告诉他送到 301。

这里：
- 你 = 应用代码（app_telemetry.c）
- 前台 = vofa 模块
- 送外卖 = 发送数据
- "让他送到 301" = 注册 writer 函数

### 9.4 JustFloat vs CSV vs FireWater

VOFA+ 支持多种协议：

| 协议 | 格式 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **JustFloat** | 二进制 float + 帧尾 | 高效、精度无损 | 不可读 | 高频实时波形 |
| CSV（文本） | `1.23,-4.56,57.80\n` | 人眼可读、跨平台 | 效率低、精度损失 | 偶尔看数据 |
| FireWater | 自定义二进制 | 灵活 | 需要自定义解析 | 高级用户 |

本工程选择 JustFloat 是因为它简单高效，适合自平衡小车的实时调试需求。
